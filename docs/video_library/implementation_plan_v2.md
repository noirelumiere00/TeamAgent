## 段階と完了条件
各段は「Codex 実装 → Claude レビュー（差分・CI と同じ依存のテスト・変異テスト・本番データ/実画面で確認）→ PR（dev 宛て）→ CI 緑 → マージ → デプロイ → 実機確認」で閉じる。

### P1 DB とシート同期（PR #742・実装済み）
- デプロイ: migration 0035 を本番 RDS に適用（`migrate_tunneled.sh dry` → 小俣さん GO → `apply`）。同期の定期実行（ingest と同じ EventBridge＋ECS の型、1日1回）を terraform で追加（既定 OFF の enable 変数＋tfvars で ON）
- 実機確認: run-task で1回流し、`vl_ingest_runs` と件数（ユニーク約2,811・organic 1,304・PR 1,507）を確認

### P2a サムネイルを S3 へ
- 新規動画のカバー画像を取得して S3 に保存（`media_jobs` バケットの prefix を流用できるか確認、無理なら最小のバケット）。取得失敗は記録し次回再試行
- カバー URL の取得方法はまず実測で決める（yt-dlp のメタデータ／既存 tiktok_scraper）。10本で成功率を測ってから全件
- 同期ジョブの後段として同じ定期実行で動かす（新規分だけ）

### P3 社内の箱 `/library`（connect_web）
- 一覧・検索（フリーワード・区分・業種・アカウント・期間・PR 印）・並び替え（再生・保存率・ENG率）・サムネ表示・TikTok へのリンク・選んだ URL のコピー
- 管理画面（小俣さんのみ）：①案件の種別・業種・目的・非公開 ②アカウント一覧・登録。設定テーブル（`vl_campaign_settings` / `vl_account_settings`、更新者・更新日時つき）を追加し、同期は有効値（Web ＞ 台帳 ＞ 未設定）で区分を決める。案件マスタのタブ読みは削除
- 管理者の判定は env の管理者リスト（個人のハードコード禁止）。閲覧の許可は既存の `CONNECT_SEARCH_ALLOWED_EMAILS`（本番で明示されているか確認）
- 実機確認: Chrome で `/library` を開き、検索・設定変更・反映を確認

### P3b アカウント登録と自動取得
- 登録アカウントの直近の投稿（例：最新30本）を定期取得し、未登録の動画だけ追加。出どころ（own/external）・取得日・取得方法を記録。外部投稿は公開しない
- 取得手段は既存（tiktok_scraper／Apify）から実測で選ぶ。費用が出るものは事前に見積もり

### P2b 動画ファイルを S3 へ
- 新しい動画から順にバックグラウンドで保存。容量・失敗率を記録

### P4 Aico ツール `video_library_search`
- 4段ゲート（skill → factory `USE_VIDEO_LIBRARY` 既定 OFF → toolFilter.include → 本番 env）。既存の事例回答との棲み分けを description に書き、ルーティング・シミュで確認
- 実機確認: Slack で小俣さんの DM だけに送って確認

### P5 公開のメディア風アーカイブ

- DB から公開してよい項目だけを書き出した静的サイトを毎日生成し、S3＋CloudFront で配信（サブドメインの DNS が要る）
- 見せない条件（R5）をテストで固定

### P6 構成分析と点数（保留）

## アドバイザー確認後の追記（2026-10-30）
- P1 はマージ前にローカル Postgres で migration・upsert・冪等を実 DB 検証する（skip のテスト2件も DSN 付きで流す）
- CI の赤は dev 最新の CI 結果と比べて切り分け、PR 本文に結果を書く
- 本番 migration・terraform apply・ECR push・EventBridge 有効化は、AWS の資格が root のため自走しない。dry/plan を見せて小俣さんに `!` で実行してもらう
- 日次同期の terraform は既存 ingest タスクの command 違いで最小に（`enable_video_library_sync` 既定 false、tfvars で true、destroy 行ゼロを確認）

## v3：進め方の決定（2026-10-30・Fable と相談、実測で調整）
入力: 内藤さん「TTO・切り抜きも載せるならトレンドメディア風の公開サイトは不要。ビデオリリースのアーカイブのような使い方」／小俣さん「アーカイブを先に作り、構成は『近日公開』。動画→構成の向きを先に」／楢原さん「全動画の箱が機能すればいい」

- **P5（公開のメディア風サイト）は取りやめ**。社外に見せたい要望が出たら `/library` の動画詳細に期限付き共有リンクを足す（別サイトは作らない）。R5・R6・R10 は社内の `/library` に読み替える（カーソル再生と TikTok への遷移は `/library` で実装）
- **最初のリリース＝P3（社内アーカイブ `/library`）**。サムネ保存（P2a）はここに含める。実測で yt-dlp のカバー取得が 10/10 成功・平均 3.2 秒（Fable 案の「oEmbed で済ませる」は、oEmbed がサムネを返さないため不採用）
- 順番: P1 本番反映 → P3（一覧・検索・並び替え・詳細・サムネ・カーソル再生・URL コピー・管理画面＝案件の種別）→ P3b（アカウント登録＋直近投稿の差分取得）→ P4 Aico → P2b 動画ファイル保存（元動画の消失が出るまで保留）
- **構成は「近日公開」**: 動画詳細に「構成」枠と「分析準備中」の表示だけ置く。備えは `vl_video_analysis(platform, video_id, kind, version, payload JSONB, analyzed_at)` 1テーブルのみ（行が無ければ準備中、あれば表示）。構成から探す UI・点数の列は P6 で方法が決まってから
- 最初のリリースの完了条件: ①営業1名・案件進行1名が Google ログインし、区分・PR 有無・期間・フリーワードで絞り込み、動画をカーソルで確認、URL をコピーできる ②全約2,811本が一覧に出て、シート同期が毎日動く ③管理者が案件の種別を Web で設定でき、次の同期を待たずに区分へ反映される ④検索から目的の動画まで1分以内
