## 1. 目的と利用場面

検索等で見つけた約100本の投稿URLをまとめて取り込み、公開数値・投稿内容・PR表記の根拠・動画の構成を同じ詳細画面で確認できるようにする。シートへ先に転記する手間をなくす。

| 誰が | いつ | 何のために使うか |
| --- | --- | --- |
| 営業 | 提案の事例を探す時 | 「どの構成で、どれだけ再生されたか」を確認し、動画URLを提案候補にする |
| マーケ | オーガニック投稿を調べる時 | 公開数値と取得日を比較し、PR表記のある投稿と区別して傾向を見る |
| 制作 | 企画・構成を考える時 | 実動画と秒単位のテロップ・発話・映像・フック等を見比べ、構成の参考にする |

**用語の分離**：本依頼の「オーガニックの数値」は、公開ページで見える再生・いいね・コメント・シェア・保存を指す。広告管理画面で分離した純オーガニック実績を意味しない。PR投稿にも公開数値はあるため、数値の取得と投稿の分類を別に扱う。

## 2. 機能要件

### 2.1 入力

以下はMVPの提案。上限・短縮URL・対象媒体の採否は第7節で確定する。

| 項目 | 要件案 |
| --- | --- |
| 貼り方 | `/library` の「URL取り込み」から、1行1URLのテキスト欄に貼る。空行・前後の空白は無視し、確認画面に入力順と検査結果を出す |
| 件数 | 1回1〜100行の非空入力。重複除去前に数え、101行以上は取得開始前にエラー。先頭100件だけを黙って処理しない |
| 対応URL | MVPはTikTokの完全な動画URL（`https://www.tiktok.com/@…/video/…`）。HTTP・スキームなしの同形式はHTTPSへ正規化。クエリ・フラグメントは除去し、動画IDで同定する |
| 短縮URL等 | `vt.tiktok.com`・`vm.tiktok.com`・`/t/…` はMVPでは「完全URLが必要」と行単位で案内。プロフィール・検索・写真投稿・LIVEは対象外 |
| 重複 | `(platform, video_id)` で重複判定。同一バッチは取得1回、元の行には「重複」と対象動画リンクを残す。既存動画は新規作成せず「登録済み／数値更新」と区別する |
| 不正URL | URLでない行、偽ドメイン、認証情報・異常ポートを含むURLは取得せず理由を表示。他の有効行は処理可能とする |
| TikTok以外 | Instagram・YouTube等は「対象外（今回のMVP）」と表示。対応しているふりをして成功にしない |
| 開始操作 | 検査後に、対象件数・重複件数・対象外件数・有料取得の有無を見て開始。長時間のHTTP応答を待たせず、受付IDで進捗を確認できる |

確認済：`video_identity()` はTT/IG/YTの所定の完全URLを解析するが、短縮URLは展開しない（C1）。媒体を認識できることと、その媒体の公開数値を取得できることは別。

### 2.3 判定：PR表記と事業区分を分ける

**衝突あり**：D2のR3とC1・C8は「`#PR`のみでPR印、`#PR`なしはorganic」。今回の希望は「`#PR`または広告ラベルでPR／オーガニック」。ラベルだけの投稿をPR区分へ変えるかは未決（Q1）。以下の推奨案は、既存の事業区分を維持し、ラベルを別の観測情報として見せる方式。

事例の種別は同日決定どおり、メディア（NewsTV等の自社媒体に掲載）／TTO（TikTokオーガニック。外部のUGC風アカウントで大量投稿し、アルゴリズム・検索順位を狙う施策）／切り抜き／その他。`#PR`なしの自動区分organicと、台帳の「運営」から出す媒体運営名は別軸で扱う。URLだけからTTOと推定しない。

| 投稿文の取得 | `#PR` | 広告ラベル | 推奨する扱い（Q1承認後） |
| --- | --- | --- | --- |
| 成功 | あり | あり／なし／不明 | 既存のPR印あり。事業区分は案件設定、未設定なら未設定。ラベルは別表示 |
| 成功 | なし | 明示的になし | 既存どおりorganic。「#PRなし・ラベルなしを確認」と表示 |
| 成功 | なし | あり | 既存区分はorganicを維持しつつ「広告ラベルあり・要確認」。純オーガニックの抽出対象からは除外する |
| 成功 | なし | 不明 | 既存区分はorganicだが「ラベル未確認」。純オーガニック確認済みには含めない |
| 失敗 | 不明 | 任意 | 分類保留。新規動画を`is_pr=false`の既定値で通常一覧へ公開しない。既存の判定は保持 |

`#PR`はNFKC正規化・大文字小文字を吸収したタグの完全一致とし、`#PRADA`は含めない。`#ad`・`#提供`・`【PR】`等は補助根拠として記録し、ある場合は上表にかかわらず要確認として純オーガニック確認済みから除外する案。事業区分への適用はQ1で決める。表記がないだけで、実際に広告配信されていないと断定しない。

| 既存部品 | 再利用可否とコード上の根拠 |
| --- | --- |
| `find_disclosures()`（C5） | 補助根拠の抽出に利用可能。`#PR`以外にも`#ad`・`#gifted`・日本語表記・括弧内PR等を検出するため、返り値が空でないことを既存`is_pr`へ直結させない |
| `AdLabelResult`（C5） | `found`と、`label=True/False/None`を分ける考え方を利用可能。取得失敗を「ラベルなし」にしない |
| `AdLabelCheckSkill.run()`（C5） | そのまま取り込み処理には使わない。許可メール制御、有料Apify呼び出し、Slack向け整形を含み、保存・構成分析はしない。`needs_review`も広告表示チェック用であり、ライブラリ分類そのものではない |
| `AdLabelCheckInput`（C5） | 改行分割・正規化の考え方は参考になるが、`MAX_URLS=20`で重複除去後に先頭20件へ切り詰める。100件取り込みの入力処理には流用しない |
| `ApifyClient.ad_label_posts()`（C6） | 承認済みの有料代替経路の候補。TikTokでは`isSponsored`・`isAd`を解釈する。返却の`AdLabelPost`に再生等の数値は含まれず、数値取得の代替にはそのまま使えない |
| `_match_ad_label_items()`（C6） | URL／投稿IDの照合は参考。ただし残り1URL・1結果を同一とみなす補完がある。DB保存ではID確認なしの補完を採用しない |

C6の`_ad_label_flag()`は、認識したbool項目が一つでもあればそのORを返す。一部キーが欠けた状態のFalseまで「画面ラベルなしを確認」と扱えるかは**未確認**で、実画面との照合が必要。

### 2.4 保存・衝突時の優先順位

| 対象 | 既存の保存先・現状 | 追加要件案 |
| --- | --- | --- |
| 動画本体の情報 | `vl_videos`、主キー`(platform, video_id)`（C7） | URL・アカウント・投稿日・投稿文・タグを同じ行へ。サムネキー・既存分析・初回取得日時を再取り込みで消さない |

| 取得経路・操作履歴 | `origin`以外に動画単位の取得経路列はない。`vl_ingest_runs`はバッチ件数・警告等（C7） | URL手動／P3b／シートを別属性で保持。バッチID、依頼者、正規URL、行別結果、試行日時・回数を永続化する。行別の受け皿は追加が必要で、既存実行ログだけで十分とはしない |

| アカウントの自動取得 | `vl_account_settings.fetch_enabled`既定false、登録画面は登録のみ（C8・C9） | URL取り込みで勝手に定期取得対象へ登録しない。P3bの有効化と分離する |
| 案件・種別 | `vl_campaigns`、`vl_campaign_settings`、有効値ビュー（C7・C8） | URLから案件名・種別を推定しない。MVPは案件未紐付けで登録する案。案件設定・業種・目的・非公開の人の判断値は上書きしない |
| 公開数値 | `vl_metrics`の`total_plays/likes/comments/shares/saves` | 公開ページ由来はこの5列に保存する案。`organic_*`はシートの明示された内訳、`ad_*`は広告指標のまま。公開数値を純オーガニックの内訳として二重格納しない |
| 広告ラベル・判定根拠 | `is_pr`のboolのみで、ラベル・不明・根拠の列はない（C7・C8） | 有無／不明、抽出した表記、取得方法・日時を保存する拡張が必要。分析結果テーブルへ広告判定を混在させない |
| 構成分析 | `vl_video_analysis`、主キー`(platform, video_id, kind, version)`（C8） | 承認済みの実分析結果のみ保存。キュー登録や見本の表示を分析済み行にしない |

数値保存の推奨案はQ3で確認する。「オーガニック動画の公開数値」という画面上の用途と、DBの`organic_*`という広告分離済み内訳の意味を混同しない。

| 衝突するもの | 優先順位の提案 |
| --- | --- |
| 同じ動画・投稿情報 | 人の確定値 ＞ シートの有効な値 ＞ URL取得値による空欄補完。欠損で既存の有効値を消さない。投稿文変更・PR根拠の不一致は新たな観測として記録し、黙って分類を変えない |
| `origin` | シートに存在する動画の`own`をURL取り込みで`external`にしない。URL先行の`external`が後にシートへ載った時は`own`に昇格し、URL由来の履歴も残す |
| 台帳の運営 | 台帳の値を優先し、URL取得側の空値で消さない。運営名と、メディア／TTO等の事例種別は別属性 |
| 同日・同動画の指標 | シートと公開ページを別の取得元として保持。シート内訳や広告指標をURL値・NULLで上書きしない |
| 表示する指標 | URL取込動画の比較は「公開ページ」の同一取得回の5指標。既存のシート事例はシート指標を維持。取得元・取得日を明示し、指標ごとに別の取得回を混ぜない |

**現状のままでは衝突する**：C2の`_upsert()`は、渡されたモデルの非キー列をNULLも含めて更新する。C1のモデルには`origin`・案件・全指標があるため、URL側から同じ保存処理を呼ぶだけでは既存値を消し得る。同期側も含め、上記優先順位を適用する必要がある。

**数値の時系列（拡張案）**：現行`vl_metrics`の主キーは`(platform, video_id, captured_on)`で、同日の値は更新、日をまたぐと別行（C2・C7）。`read_batch()`は同期日のJST日付を付けており、シート数値そのものの観測日を保証しない（C3）。

| 追加する扱い | 要件案 |
| --- | --- |
| 取得元 | `metric_source`相当の属性を追加し、日付の主キーに取得元を含める案を推奨。既存行はシート由来、URL・P3bは公開ページ由来として区別する（列名・移行SQLは設計時） |
| 日時 | `captured_on`はJSTの日付。公開ページには実際の取得時刻も保持し、同日再取得は同じ取得元の最新成功スナップショットへ更新。日内全履歴の保存はMVP対象外 |
| 欠損・失敗 | 完全失敗では数値行を新規作成・上書きしない。一部取得のNULLはその取得回の欠損として表示する。古い値で穴埋めしない。同日更新で既存の有効値が欠ける場合は従前のスナップショットを維持し、試行履歴に部分取得を残す |
| 最新値の選択 | 取得元を先に選び、その中の最新日・時刻を読む。C9の`_METRICS_JOIN`は現状「日付の最新1行」なので、取得元別の選択へ対応させる。履歴チャートはMVP必須にしない |

### 2.6 構成分析への接続

| 段階 | 要件案 |
| --- | --- |
| 取り込み完了 | 動画IDと依頼する分析種別をキューへ登録。既存分析がある動画や同一動画・同一版の待機は重複登録しない |
| GO前 | 状態は「分析承認待ち」。URL取り込みだけで分析・動画ダウンロード・有料モデル呼び出しを開始しない |

確認済：C10に受け皿・タイムライン・タグ表示がある。C8の`vl_video_analysis`は結果テーブルであり、キュー・GO状態・ジョブ状態の列はない。永続的な待機管理の受け皿は追加が必要。既存の汎用キューを転用できるかは**未確認**。区間クリックは内容表示の切り替えで、動画の該当秒へのシーク実装は確認できていない（C10）。

## 3. 数値の更新

シート同期の頻度とは別に決める。過去の日付へ最新累計を遡って埋めず、「いつ見た累計値か」を残す。

| 案 | 動作 | 利点・負担 | 推奨 |
| --- | --- | --- | --- |
| A：初回のみ | 取り込んだ時点の数値で固定 | 最小の取得量。比較日が古くなる | 固定した調査記録だけなら可 |
| B：初回＋手動更新 | 管理者が選んだ最大100本を再取得 | 必要な時だけ最新化。ブロック・費用を管理しやすい | **MVP推奨** |
| C：対象限定の日次 | 新規投稿後30日など、指定期間・対象だけ日次取得 | 伸びの比較が可能。対象増加で通信・費用・失敗も増える | 次段階の候補。期間・上限は未決 |
| D：週次更新 | 対象を週1回取得 | 日次より軽く、古さを抑えられる | 継続比較が必要なら候補 |

推奨Bでも再取り込みを重複登録で終わらせず、指標の更新要求として扱えるようにする。定期更新は既定OFFとし、Q4で頻度・対象・停止条件を決めてから有効化する。

## 4. 非機能要件

| 項目 | 要件案・確認事項 |
| --- | --- |
| 頻度制限 | 同一取得先への処理は全バッチ・P3b・サムネで共通の制限をかけ、MVPは直列・投稿ページへのアクセス間隔1秒以上を推奨。1回100本の上限に加え、再試行分も総アクセス数に含める |
| 既存の停止条件 | `fill_thumbnails()`は既定上限300、間隔1秒、429で停止、連続5件失敗で停止、HTTPタイムアウト20秒（C4）。URL取得にも同じ考え方を適用し、停止した残りを「未処理」とする |
| TikTokのブロック | 依頼者共有の実績：素のUAでは約1.4KBの空ページ、完全なChrome UAで約95%成功、取れない動画は約6%。分母・期間が不明で、95%と6%を同一標本の補数とは扱わない。C4にも短いUAでJSONなしになる旨と完全UAの実装がある。実績は将来の成功保証ではない |
| 成功判定 | HTTP 200だけでは成功にしない。必要JSON、投稿ID、対象データを検証し、空ページ・チャレンジ画面は失敗／取得制限とする |
| 再試行 | 一時的通信失敗は間隔を延ばして最大2回の追加試行を推奨。429は同バッチで即再試行せず停止。403・チャレンジは取得制限として停止し、認証・CAPTCHA回避を自動化しない。再開は管理者操作または承認済みスケジュール |
| 個別失敗 | 削除・非公開・地域制限・通信失敗を、確認できる範囲で区別。不明な失敗を「削除」と断定しない。正常行は保存し、一件の失敗で全件を破棄しない |
| 再開・整合性 | 行別に保存結果を確定し、中断後は失敗・未処理分から再開。DB書き込み失敗を成功表示せず、再送・二重クリック・並行実行でも同じ動画・分析待ちを重複作成しない |
| URL安全性 | 許可ホスト・パス・ポート・IDを検査し、任意URL取得を許さない。短縮URLを将来扱う場合も各リダイレクト先を検査。画像はC4のCDN許可、JPEG検査、最大5MiB、リダイレクト非追従を維持 |
| 権限 | 社内ドメインの閲覧、管理者は小俣さんのみという同日前提を維持。実装は既存認証・管理者リストを利用（C9）。本番のドメイン・メール設定値は未確認。取り込み権限はQ2 |
| 費用 | ページ取得・画像保存でも実行基盤・S3・通信費が発生するため無料とはしない。URL取得とP6分析の費用を分け、100本の実測時間・通信量・失敗率から見積もる。金額は未確認 |
| 有料代替 | ApifyはC5の`CostGuard`と費用記録を参考に、100本あたり／月次の上限・停止条件を事前提示。予算承認なしで自動フォールバックしない。取得の再利用による二重課金防止も要件にする |
| 個人情報 | 保存対象は必要な公開投稿情報のみ。コメント本文・コメント投稿者一覧・非公開プロフィール・ログイン資格情報は収集対象外。操作履歴の社員メールは管理用に閲覧を制限する |
| ログ・保存期間 | 運用ログは受付ID・動画ID・状態・件数・費用を中心にし、投稿文・追跡パラメータ・HTML全文・秘密情報を出さない。行別履歴・証跡の保存期間と削除受付窓口はQ9で決める |
| 規約・権利 | 自動取得・サムネ保存・外部サービスへの送付・分析用一時保存の利用条件と社内確認先を、運用開始前に確認する。公開情報であることを再利用許諾とはみなさない。現行の適用規約・許諾状況・法的評価は**未確認** |
| 公開・変更 | 外部一般投稿を社外へ自動公開しない。公開サイトを再開せず、社内`/library`で利用。送信・本番変更は小俣さんのGO後という同日前提を維持する |

## 5. P3bとの共通化案

**妥当と考える**。入力URLを得る工程と、1本の投稿を取得・検査・保存する工程を分ければ、数値・PR根拠・失敗の扱いを統一できる。共通化は取得と保存の中核を対象にし、アカウント列挙やシート同期まで同じ入力仕様へ押し込まない。

| 部品・入口 | 責務 | 共通化しない点・条件 |
| --- | --- | --- |
| URL貼り付け入口 | 最大100件の入力検査、重複表示、操作履歴 | 入力者・バッチの権限と受付画面 |
| P3bの入口 | `fetch_enabled`の登録アカウントから直近投稿URLを列挙し、原則未登録分を渡す | 最新何本／何日、列挙方法・費用、差分位置の保持はP3bで決定。過去全件を繰り返し集めない（D2 R8） |
| 「URL1本を取り込む部品」 | 正規化・ID確認 → 公開情報取得 → 表記／ラベル観測 → 優先順位を守って保存 → サムネ → 分析承認待ち登録 | 取得元・操作主体・`origin`の根拠を受け取る。取得と同時に分析実行やアカウント定期取得を始めない |
| 数値の再取得 | 登録済みIDを同じ取得部品へ渡して新しい観測を保存 | P3bの「新規URL発見」と更新スケジュールを分離する |
| 共通の制限・記録 | 同じ動画の重複処理抑止、アクセス間隔、予算、429停止、取得日時・失敗分類 | P3bが別ジョブでもTikTokへの総アクセス量を制御する |

C4のページJSON・カバー取得は共通化の出発点になるが、現在の関数はカバーURLしか返さない。投稿ページをメタデータ・ラベル・サムネごとに重複取得しない構成にする。P3bのアカウント列挙手段が同じJSONで実現できるかは**未確認**。

VCL・gracemodeが現状DBに0本なのは「元シートにない」という依頼者共有の現状で、DB再集計は未実施。URL取り込みは指定された投稿だけを補い、台帳アカウント全体の網羅はP3bで扱う。

| A11 | 保存率・ENG率、再生0・4,999・5,000、一部指標欠損 | 既存式と一致し、算出不可・参考値の境界が正しい。公開値と広告指標を足し合わせない |

| A14 | 100本の承認済み実測 | 母数・日時・環境・所要時間・成功／一部取得／失敗理由・リクエスト数・費用を報告。100行すべてに終端または未処理状態があり、成功率が低い場合の運用可否は小俣さんが判断 |
