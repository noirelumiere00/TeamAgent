# 長い作業の通知（P4）

お土産資料、TikTok 取得、動画分析、提案書の通知は
`mcp_gateway/async_job_notify.py` に集約する。宛先は gateway が検証した
caller claim の依頼元 DM／スレッドだけ。退避 DM も同じ claim の Slack ID だけを使う。
投稿・添付は既存 bot token の経路を使い、権限を追加しない。

- `USE_LONG_JOB_NOTIFY`: 既定 ON。OFF で共通監視、直近ジョブの自動照会、添付の遅延配信を止める。
- `USE_LONG_JOB_RETRY`: 既定 ON。取得・ローカルの資料生成を同じ入力で一度だけ再試行する。
  公開・Slack 投稿・quota 予約・結果保存を含むジョブ全体は再実行しない。
- 動画の旧 `USE_VIDEO_ALGORITHM_DETACH` を明示した場合、その値と旧 rollout 設定を優先する。
  未設定なら共通通知 ON のとき本人確認済み利用者の依頼を切り離す。
  実行数・待ち行列・入力・読む動画は既存のまま。

資料の添付は一時ファイルを確保し、台帳の `done` 保存を確認してから行う。
完了文・要点は最初の添付コメントにまとめ、完了だけの追加メッセージは出さない。
失敗時は例外本文を表示せず、確認できた原因を一行にする。

監視は30秒間隔。60分を超えたときは一度だけ、未完了または状態確認不能を知らせる。
停止とは断定せず、その後も監視し、保存された結果を届ける（監視上限24時間）。
SIGTERM 時には配信の監視が中断したことを知らせる。別 worker の実行停止を推測しない。

通知済みの錠、本人・会話ごとの直近ジョブ参照、未通知の一覧は既存
`PROPOSAL_JOBS_TABLE` の `dedup_` キーを使う。GetItem／PutItem／既存の結果更新だけで、
Scan・GSI・新しいテーブルは使わない。HTTP／stdio 起動時に未通知の監視を再開する。
別の MCP の監視が180秒以内に更新した項目は奪わない。
未通知一覧は本文・email・token を持たず、検証済みの宛先、本人識別子、
取得主体のハッシュ、ジョブ参照、時刻だけを持つ。

`*_status` の `job_id` 省略時は本人の直近を引く。チャンネルでは同じチャンネルの参照だけ。
複数キーワードの取得は分割ジョブ全部の状態を返し、一つだけ終わった段階で全体の完了を名乗らない。
動画分析は台帳の状態と実行中の登録簿・心拍を確認し、別人の番号では結果を返さない。
復旧後に添付ファイルを保持していない資料は、配信中断として知らせる。

Slack の応答タイムアウトは配信済みの可能性があるため再送しない（既存の重複回避契約）。
`PROPOSAL_JOBS_TABLE` 未設定のローカル実行では台帳はメモリで、再起動復旧はできない。
稼働環境の確認・点灯・外部接続はこの変更には含めない。
