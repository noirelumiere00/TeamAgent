# Obsidian-Parity Build Plan — `connect_web` (read-only knowledge graph)

Grounded in the real code: `app.py` (905 lines) has two standalone pages built by `_search_page`/`_graph_page`, two style strings `_SEARCH_STYLE`/`_GRAPH_STYLE`, two JS engines `_SEARCH_JS`/`_GRAPH_JS`, route handlers `search_ui`/`search_graph_ui`/`api_search`/`api_graph`/`api_feedback`, and the RLS helper `_list_graph_docs(email)`. Graph math lives in `graph.py:build_graph(docs, *, max_degree=6)`.

**Three load-bearing facts the specs got wrong — the plan accounts for these:**
1. **Graph node `id` is an integer `node_id` (`abs(hashtext(d.id))`), NOT the url.** `node.url` = `source_uri`, which can be null or non-unique. So `/api/v1/related?doc_id=<source_uri>` and any "url→node map" must tolerate null/duplicate urls; key the related lookup by `node_id` where possible and pass `node_id` through to the client.
2. **`client_name` is consumed for edges but NOT emitted on graph nodes** (`graph.py` lines 59–69). Adding it is the one-line backward-compatible field add the panel/tags need.
3. **`deal_phase` exists only on search hits, not in the graph payload** — `list_documents_for_graph` never selects it. Drop `deal_phase` from any graph-node/related expectation.

Everything below is dependency-free vanilla JS, `textContent`-only for dynamic strings, single canvas, RLS untouched (all data still flows through `_list_graph_docs(email)` / `api_search`'s RLS `SkillContext`).
