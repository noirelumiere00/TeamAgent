## 今回の変更

公開入口 `SearchSkill.run` に、全経路から返った不在候補を受ける共通段を追加。
`SEARCH_NOT_FOUND_RECOVERY` は既定ON。`0`（または `false`）で共通段全体とキャッシュを止め、
従来の検索経路へ直接戻す。既存の別名・fanout・表示用の各フラグはそのまま有効。
既存フラグも停止した場合は検索1回・範囲フッターなしに戻ることを、元の
`test_kill_switches_restore_single_search_and_no_footer` で確認する。
初回で資料または表示可能なSlack根拠がある場合は終了する。
不在候補なら既存fanoutを使い、同じ本人/RLS・明示フィルタで次を最大2段試す。

1. 既存の全半角・法人格・別名展開、金庫・Slack・名指し資料・カルテ・構造化事例。
   金庫の取得閾値を0.16まで緩める。カルテ・構造化事例の照合条件は既存部品に従い、対象不明なら未実行と示す。
2. まだなければ取得/存在判定の閾値を既存fallbackの0.05まで緩める。
   指定企業・主題の一致は保ち、弱い根拠は低信頼として表示する。

Driveの原本がない場合は、取得できた会話・記録をその種類のまま返す。
推測した別業種を元の問いの存在根拠にはしない。共有Skillの設定は変更しない。
全段で見つからず必要な検索が完了したときだけ不在を確定し、検索先と実際の検索語を1行で付ける。
失敗・未連携・非公開の一致は不在と区別し、探し直しを利用者へ返す `suggested_next` を外す。

埋め込みは初回・別名・閾値緩和の全段でリクエスト内のキャッシュを共有する。
同じ語の並行要求も1回にまとめ、別のリクエストへは持ち越さない。
別名なしは全段で計1回、元の語と別名1つなら計2回。別名OFFは救済段でも尊重する。
閾値緩和の2段目では、救済段で完了済みのSlack検索も再実行しない（失敗時は再試行）。

## 追加呼び出し数と遅延の概算

実サービスの平均時間は未取得なので、以下の秒数は**仮の平均時間による計画値**。
初回不在から2段とも実行し、planner/HyDEによる新語生成・API内部リトライ・ページ追加なしを前提にする。
別名数を `A`（0〜2）、救済で初めて使う語数を `E`（既存別名検索で試行済みなら0）とする。

| 処理 | 従来経路に対する追加回数 | 仮の平均時間 |
|---|---:|---:|
| 埋め込み | 同じ語は0回。新しい語だけE回 | 0.20秒/語 |
| DB取得 | `2 × (1 + A)` 回のretrieval（内部SQL・構造化取得を含む論理呼出し） | 0.15秒/retrieval、rerank・埋め込みを除く |
| Cohere rerank | 0〜`2 × (1 + A)` 回。候補0件なら0回 | 0.40秒/回 |
| Slack API | 完了する検索1組、1〜3回。次の閾値段はキャッシュ | 0.30秒/回 |

直列に足した見積りは `E×0.20 + DB回数×0.15 + rerank回数×0.40 + Slack回数×0.30` 秒。
たとえば別名1つを初回で試行済みなら、追加埋め込みは0回。
全候補0件では `0 + 4×0.15 + 0 + (1〜3)×0.30 = 約0.9〜1.5秒`、
弱い候補のrerankも4回必要なら `約2.5〜3.1秒`。
別名なしの全候補0件なら `約0.6〜1.2秒`。救済OFFまたは初回で見つかった場合は追加0回・0秒。

SlackとDB、別名ごとのretrievalには並列部分があるため、上記は並列短縮を見込まない概算。
SQL数・候補数・APIリトライ・タイムアウト・plannerの新語生成で時間は増えうる。
本番平均での遅延・改善率は未計測。フェイクの実行時間を本番平均としては使っていない。
